# Документация архитектуры

Структура `docs/architecture/`:

- `ARCHITECTURE.md` — только карта модулей библиотеки и как они связаны между собой, от общего к
  частному. Без деталей пайплайна внутри отдельного модуля.
- `modules/<module>.md` — архитектура одного модуля. Модуль — это самодостаточный подпакет уровня
  `core/<module>/` (например `region_seg`), а не отдельный `.py` файл внутри него.
  Диаграммы (mermaid), таблицы, формулы, сквозные конвенции, которые не принадлежат ни одной
  отдельной функции. Не дублировать Parameters/Returns/Raises из докстрингов — докстринги сами
  станут документацией через mkdocstrings.
- `decisions/<module>.md` — по тому же модулю: известные проблемы (статус открыто/решено, что
  планируем попробовать дальше) и отброшенные альтернативы (что пробовали и почему не сработало).
  Не changelog и не diff — решения и проблемы конкретно по алгоритму модуля.

Перед началом работы над каким-либо модулем сначала читай `modules/<module>.md` и
`decisions/<module>.md`, если они существуют, — там актуальный контекст задач и открытых проблем.

При создании нового подпакета в `core/` заводи пару `modules/<name>.md` + `decisions/<name>.md` и
добавляй строку в таблицу модулей в `ARCHITECTURE.md`.

## Формат markdown-документации

Документация собирается позже в MkDocs (Material). Пиши сразу под это:

- Диаграммы — mermaid (` ```mermaid `), рендерится и в MkDocs, и при обычном просмотре на GitHub.
- Формулы — LaTeX, `$...$` / `$$...$$` (расширение `pymdownx.arithmatex`).
- Заметки/предупреждения — admonition-синтаксис MkDocs Material (`!!! note`, `!!! warning`,
  `!!! tip`), не GitHub-специфичный `> [!WARNING]`.

# Строгость типов: граница модуля против внутренней реализации

Правило разделяет код по видимости функции, а не по модулю целиком.

**Публичная функция** (без `_`, вызываемая из другого файла) — межмодульная граница:

- параметры и возврат типизированы через alias из `core/types.py` (`Mat`, `Array[DType]`,
  `Array2D[DType]`, ...), с точным dtype в месте использования, а не общим `Array1D`-подобным
  союзом;
- множественный результат — `frozen dataclass` (например `ComponentLabels`,
  `ComponentClassification`, `Groups`), не кортеж;
- докстринг — полный numpy-стиль (`Parameters`/`Returns`/`Raises`).

Это же касается `pipeline.py` целиком — единственной точки входа модуля наружу и будущего CLI.

**Приватная функция** (`_...`), используемая только внутри одного файла для разгрузки его
единственной публичной функции, — внутренняя реализация:

- возврат — обычный кортеж/массив, не обязательно dataclass;
- докстринг — одна строка или не нужен вовсе, если имя и контекст самоочевидны;
- локальная переменная аннотируется типом, только если тип не следует однозначно из сигнатуры
  вызываемой функции.

Обоснование: тяжёлая типизация — осознанное решение проекта ради будущей библиотеки с CLI.
Строгость оправдана только на границе, которую видит другой модуль, не читая реализацию.

# Имена

Во всём коде — модули, публичные функции, блокноты — короткие имена в стиле OpenCV/CV:
`img`, `gray`, `binary`, `cnts`, `labels`, `stats`, `comp_area`, `img_h`/`img_w`, `thresh`,
`hor_kernel`/`ver_lines`. Не `component_area`, `image_height`, `thickness_threshold`.

# Тесты

- Юнит-тесты — в `test/unit/`, интеграционные — в `test/integration/`.
- Не только параметризованные тесты, без переусердствования. Общие фикстуры — в `conftest.py`.
- Тест помечается ID требования канона: `@pytest.mark.req("DEL-07")`. Интеграционные — ещё и
  `@pytest.mark.integration`; данные из `data/` не в git, без них тест пропускается.
- Стенды прогона — модули в `notebooks/`, результаты — в `research/results/`.

# Блокноты

- Каждая ячейка — логически завершённая подзадача с выводом: принт, график или изображение.
- Константа объявляется в той ячейке, где используется, а не в общей ячейке констант.

# Чистый код: DRY, KISS, YAGNI

- **DRY** — реальное дублирование (одна и та же формула/логика в нескольких местах) выносится в
  функцию один раз. Пример: `_pairwise_overlap`/`_pairwise_gap`/`_pairwise_mean` в
  `region_merging.py` — одна формула, применяется к двум осям вместо копипаста x/y-версий.
- **KISS** — простое решение предпочтительнее «умного», если оно решает задачу не хуже. Пример:
  вложенный Python-цикл для поиска пар на слияние вместо плотной NxN-матрицы — при реалистичных
  объёмах данных (проверено на числах) читается прямо в лоб и не медленнее.
- **YAGNI** — не добавлять абстракцию/параметр/тип «на будущее» без текущего вызывающего кода.
  Пример: `Vec`, `Vec2D`, `Vec3D`, `Point`, `Point2D` убраны из `core/types.py`, потому что ни
  один реальный вызов их не использовал — остались только `Array`/`Array2D`/`Mat`, у которых есть
  реальные потребители. Заводить их снова — только когда появится конкретное место использования,
  не заранее.

**Паттерны проектирования — только при доказанной необходимости, и не должны усложнять логику.**
Если применение паттерна (фабрика, стратегия, DI-контейнер и т.п.) добавляет уровней косвенности
без того, чтобы решить реальную, уже существующую проблему — не применяй его. Это не отменяет
SOLID целиком, но SOLID (в первую очередь буквы про интерфейсы/наследование/инверсию зависимостей)
применим только там, где в коде уже есть классы и иерархии — не переносить его на функциональный
код на `frozen dataclass` + чистых функциях, который является стилем проекта по умолчанию.
