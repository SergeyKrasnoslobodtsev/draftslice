# Решения: ocr

## Известные проблемы

### IoU по осевому прямоугольнику {#iou-по-осевому-прямоугольнику}

**Статус:** открыто, не встречалось на реальных данных.

`filter_results` считает перекрытие двух результатов по IoU осевых прямоугольников (bounding box)
их полигонов, а не по пересечению самих четырёхугольников. Для сильно повёрнутого (близко к 45°)
текста осевой прямоугольник может быть заметно больше самого полигона, из-за чего два реально
разных, но расположенных по диагонали друг от друга текста могут ошибочно посчитаться дублями.
На чертежах текст обычно повёрнут на 0°/90°/180°/270°, где осевой прямоугольник совпадает с
истинной формой полигона - проблема актуальна только для произвольных углов, которых пока не
встречалось.

### Фиксированный набор углов поворота

**Статус:** открыто, не начато.

`PaddleOCRParameters.angles` по умолчанию `(0, 90, 270)` - подобрано по тому, как обычно
ориентирован текст на этих чертежах (горизонтально или вдоль вертикальных размерных линий).
Текст, идущий под произвольным углом (например, вдоль наклонной выносной линии), не будет найден
ни на одном из трёх поворотов. Пока не встречалось как реальная проблема.

### Пороги `text_rec_score_thresh` / `iou_threshold` подобраны эмпирически

**Статус:** открыто, не начато.

Оба порога - обычные константы, не выведены из статистики конкретного изображения (в отличие,
например, от адаптивного толеранса толщины в модуле классификации линий). Не проверялась
устойчивость на чертежах другого качества скана/разрешения.

## Отброшенные альтернативы

### `use_textline_orientation=True` вместо поворота всего листа {#почему-не-usetextlineorientation}

Встроенный в PaddleOCR/PaddleX классификатор ориентации текстовой строки выглядел как прямое
решение задачи с повёрнutым текстом, но при чтении исходников `paddlex.inference.pipelines.ocr.pipeline`
выяснилось: его `rotate_image` принимает только индикатор `0`/`1`, что соответствует повороту на
`0°` или `180°` - он в принципе не умеет корректировать 90°/270°, которые на этих чертежах и есть
основной случай (размерные надписи вдоль вертикальных линий). Заменено на поворот всего листа на
нескольких углах и повторный прогон полного пайплайна детекция+распознавание на каждом.

### `use_doc_orientation_classify` для поворота

Не подходит по смыслу - это классификация ориентации всего *отсканированного/сфотографированного
документа целиком* (например, скан вверх ногами), а не отдельных текстовых строк на плоском,
корректно ориентированном скане чертежа.
